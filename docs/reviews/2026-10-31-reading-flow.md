# 혼디 한 페이지 읽기 UI 독립 마감 검토

확인일: 2026-10-31. 읽기 전용 검토. 검토 시 checkout HEAD는 `c44b1b9`이며 `bebde14`의 문의처 선택/준비 결과 구분을 포함한다. root의 문서·eval 미커밋 변경은 검토 대상 UI 수정으로 취급하지 않았다.

## 판정

**시각 구성과 문서 읽기 흐름은 채택 가능하다. 진행 갱신 중 처리 근거 링크의 포커스 보존 1건을 고친 뒤 최종 통합 QA를 마쳐야 한다.**

이 변경은 2×2와 선택한 작은 창을 없애고, 자료·병원·이동/동행의 요약 아래에서 대화 전체를 읽게 한다. 준비 내역은 페이지 안에서 펼치며 공통 입력은 하나다. 사용자 요구 밖의 새 시각 방향이나 UI 확장은 필요하지 않다.

기준은 `docs/reading-flow-contract.md`와 최신 AGENTS/PRODUCT다. Operate 모드의 Impeccable `SKILL.md`, `reference/operate.md`, `craft-floor.md`, `polish.md` 및 Ponytail review 기준을 읽었다. context launcher는 상위 작업의 exit126/수동 context 사실을 이어받았으며 재실행·수리하지 않았다.

## 유지할 내용

- **페이지 전체로 읽는 구조:** `app/conversation.css:198–199, 221–238, 302`에서 준비판·작업면·답변·방문 상세의 높이를 문서 흐름으로 푼다. 현재 렌더의 접힌 내역, 펼친 PC·모바일 내역, 긴 답변에 독립 세로 스크롤 막대나 잘린 고정 창이 보이지 않는다. 별도 기록/전화/여정/선택 답변 dialog, 설정 서랍, 긴 textarea와 표의 가로 스크롤은 계약의 예외 범위다.
- **세 가지 상태만 먼저 읽기:** 상단의 자료 확인·병원 문의·이동/동행이 ○/△/×와 결과 있음·추가 확인·실패/인계를 함께 사용한다. 상태는 SVG와 텍스트로 표현하며 색만으로 전달하지 않는다. preview에서는 자료 △, 병원 ○, 이동/동행 ×가 한눈에 구분된다. 중립 대시는 확인 전/불필요를 구분한다.
- **준비 상태와 실제 진행의 분리:** `getPreparationBoard`의 signal은 기존 상태를 읽는 projection이다. 자료 누락은 △이며 실제 문의 실패/인계가 ×다. 현재 소스는 문의처만 골랐을 때 이동 준비를 ○로 바꾸지 않는다(`app/preparation-stages.js:112–118`). 실제 진행은 pending·검증된 running DTO·관측 도구를 따로 사용한다(`app/preparation-board-view.js:36–65`). ○를 진료·예약·배차 확정으로 설명하지 않는다.
- **새 답변과 내역의 위치:** `startProgress → renderBoard → renderPreparationBoard`에는 `openStage`, `focus`, `scrollIntoView` 호출이 없다. 진행만으로 native details의 open 값을 변경하지도 않는다. 요약 버튼은 `openStage`에서 사용자가 고른 내역을 열고 해당 섹션에 초점을 둔다. 최종 응답은 `scrollToMessage`로 새 답변의 시작을 보이게 한다. 다만 아래 필수 수정의 DOM 교체는 간접적으로 포커스를 잃게 한다.
- **모바일 입력과 장문:** 초기 390×844·360×780 캡처에서는 입력과 보내기가 보인다. 390×500은 문서 스크롤로 접근하는 구성이다. 긴 답변의 시작과 마지막 안내를 직접 열어 보았으며, 200% 글자 캡처에서 본문 줄바꿈을 유지한다. 6개 크기의 기존 관측 JSON은 문서 폭 넘침 없음, 첫/끝 문장·입력·전송·두 고지 도달 가능을 보고한다. 이는 이번 리뷰에서 재실행한 결과가 아니다.
- **브랜드와 정보 밀도:** 사용자 지정 로고·인물 없는 제주 바다/현무암 배경·Pretendard가 유지된다. 청색 본문과 행동, 녹색/황갈색/붉은 상태 의미가 일관된다. 카드 벽을 새로 만들지 않고 하나의 답변 면과 얇은 준비 행을 쓴다. 기존 현재/다음 행동과 출처·합성 표시는 남아 있다.
- **좁은 변경 범위:** 새로운 의존성·저장·API를 추가하지 않았다. 강제 창 높이와 확대 전환을 관리하던 ResizeObserver/visualViewport 코드를 제거하고 native details와 문서 흐름을 사용한다. 이번 검토에서 별도 구조 재작성이나 기능 삭제를 요구할 정도의 중복/복잡성은 찾지 못했다.

## 필수 수정

1. **진행 갱신이 처리 근거 링크의 키보드 포커스를 제거한다.**

   근거: `app/preparation-board-view.js:24–25, 70–76`, 호출 경로 `app/conversation.js:607–630`.

   이전 성공 응답에 병원 조회/문의 초안 등의 출처 URL을 가진 event가 남아 있는 상태에서 다음 요청을 보낸다. 보호자가 준비 내역과 해당 처리 기록을 펼쳐 이전 event의 ‘처리 근거’ 링크에 키보드 포커스를 두고 읽는 동안, 같은 단계의 새 progress event가 들어오면 `liveEvents`가 달라진다. `replaceMarkup`가 `[data-stage-events]` 전체의 `innerHTML`을 교체해 포커스를 가진 기존 앵커도 제거한다. 브라우저는 그 앵커의 포커스를 유지할 수 없다.

   실제 source가 있는 event는 `agent/tools.mjs:353, 368, 450` 등에서 생성되고, 요청 시작은 `latestEvents`를 지우지 않는다. 따라서 추정한 입력 형식이나 비정상 DTO가 필요한 사례가 아니다. 다만 이번 작업은 테스트 금지 범위여서 소스 추적으로 판정했으며 독립 브라우저 재현은 하지 않았다.

   최소 수정은 기존 최종 event DOM을 보존하면서 진행 event의 li만 추가/갱신하는 것이다. 전체 교체를 유지한다면 교체 전의 포커스가 해당 영역 안에 있을 때 같은 event/source로 복원해야 하며 읽던 위치도 유지해야 한다. 진행을 중단하거나 출처 링크를 없애는 수정은 필요하지 않다.

   회귀 확인은 ‘이전 source event가 있는 두 번째 요청 → 처리 근거 링크 focus → 동일 단계 progress 갱신 → 동일 링크 focus·details open·페이지 읽던 위치 유지’ 한 사례면 된다. 현재 QA 소스의 진행 포커스 검사는 입력칸만 확인하므로 이 경로를 잡지 못한다(`scripts/preparation-board-browser-check.mjs:276–278`, 리뷰 시점).

## 직접 확인한 화면과 관측 자료

파일 존재를 먼저 확인하고 다음 PNG를 `view_image`로 직접 열었다. 다른 에이전트의 화면 인상만 전달받아 완료하지 않았다.

- `initial-1440x900`, `initial-1280x800`, `initial-390x844`, `initial-360x780`, `initial-390x500`
- `preview-1440x900`, `preview-390x844`, `expanded-1440x900`, `expanded-390x844`
- `details-1440x900`, `details-390x844`, `details-360x780`, `details-390x500`, `details-768x512`
- `long-1440x900`, `long-390x844`, `long-360x780`, `long-390x500`
- `large-1440x900`, `large-390x844`, `large-360x780`, `large-390x500`, `large-768x512`
- `last-1440x900`, `last-390x844`

경로는 `/tmp/hondi-reading-ui/`이며 확장자는 `.png`다. 초기/preview/expanded 일부는 전체 문서 캡처이므로 파일명의 viewport 높이를 전체 이미지 높이로 오해하지 않았다. last는 끝 문장 요소 캡처다.

`long-results.json` 및 생성 스크립트 `long-check.mjs`도 읽었다. 1440×900·1280×800·390×844·360×780·390×500·768×512의 기존 own-UI 관측은 준비 내역 펼침 후 문서 높이가 각각 2586→4215 / 2586→4215 / 3249→5121 / 3249→5173 / 3249→5121 / 2581→4196으로 늘어남을 기록한다. 대상 준비/답변/방문 컨테이너는 `height:auto`, `max-height:none`, `overflow-y:visible`이다. 표는 모바일에서 가로 이동하며 자체 높이 제한은 없다. CSS 전체 글자 크기를 두 배로 만든 검사는 실제 브라우저 줌/실기기 키보드 검증과 구분한다.

## 한계와 최종 통합 확인

- 저장소 파일 수정, 테스트 실행, 서버 기동, 원격 접근, 키 읽기, 실모델 호출은 하지 않았다. 유일한 산출물은 이 `/tmp` 보고서다.
- 캡처는 UI 담당자가 자기 작업 환경에서 만든 결과이며 current 통합 checkout의 최종 fresh QA 결과로 확대하지 않는다. 기본 signal 검토는 `bebde14`를 포함한 current 소스를 따랐다. 문의처만 선택한 상태의 △ 동작을 해당 기존 PNG로 새로 증명했다고 주장하지 않는다.
- 실제 음성 인식, 스마트폰 가상 키보드, Safari/Firefox, OS/브라우저 200% 줌, 스크린리더, 유료 모델/기관 연계는 미검증이다.
- root가 예정한 통합 후 fresh 브라우저 3종과 단위/eval은 별도다. 리뷰 당시 브라우저 QA 소스에 이전 2×2 단언이 남아 있었으며 QA 담당 갱신/통합을 기다리는 것으로 이해했다. 이전 실행 기록을 새 배치의 통과로 해석하지 않았다.

## 문서 갱신 필요

최종 UI 수정 후 root/documenter가 `DESIGN.md`와 `.impeccable/design.json`을 실제 CSS에 맞춰 갱신해야 한다. 두 문서는 현재 PC2×2·모바일 한 창 선택·창 내부 스크롤·고정 높이·이전 녹색/귤색 행동·이전 focus 수치를 담고 있다. 실제 현재 기준은 `app/conversation.css:3–4, 192–374`다.

갱신 항목은 읽기 계약의 우선순위, 세 상태 요약/native details/항상 읽는 답변, 문서 스크롤과 허용 예외, 새 색 토큰·Pretendard 제목·본문16px/행간, 주요44px 조작, 6개 확인 크기와 200% 글자 관측 범위다. `docs/preparation-board-contract.md`와 `docs/editorial-ui-contract.md`의 이전 배치/색 문구는 이력임을 명시하거나 최신 계약 링크로 우선순위를 고정하면 된다. 오래된 지침으로 새 화면을 되돌릴 근거로 사용하면 안 된다.

**최종 판정: 필수 수정 1번과 문서 정합화, 예정한 최종 통합 QA를 마친 뒤 배포 가능. 추가 시각 재설계는 필요 없음.**
