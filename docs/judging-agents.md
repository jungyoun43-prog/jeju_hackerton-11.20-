# 평가기준별 모의 심사 에이전트

작성일: 2026-10-31. 공식 기준 출처와 확인 범위는 [수상 전략](award-strategy.md)에 있다.

이 문서는 개발 중 반복해서 사용할 **심사 역할·입력·출력 규약**이다. 2026-10-31에는 아래 5개 역할로 실제 서브에이전트를 실행했다. 상시 실행되는 시스템이나 API 기반 자동 실행기는 아직 구현하지 않았다.

## 구성과 운영

| 역할 ID | 담당 공식 항목 | 배점 | 대표 질문 |
| --- | --- | ---: | --- |
| `judge_topic` | 분석 주제의 타당성과 창의성 | 15 | 누가 어떤 판단을 더 잘하게 되며, 기존 방식과 무엇이 다른가? |
| `judge_data` | 필수 데이터 활용 적절성 | 20 | 지정 자료가 실제로 어느 수치와 결론을 결정하는가? |
| `judge_agent` | AI Agent 기술성 및 완성도 | 25 | 목표에 맞는 도구를 실제로 실행하고 오류에 대응하는가? |
| `judge_usability` | 편의성 및 실용성 | 25 | 처음 접한 비전문가가 과업을 완료하고 결과를 활용할 수 있는가? |
| `judge_reliability` | 결과 신뢰성 및 재현성 | 15 | 수치의 근거를 추적하고 다른 환경에서 다시 계산할 수 있는가? |

조정자는 같은 버전의 자료를 5개 평가자에게 전달하고, 각 평가자는 다른 평가자의 결론을 보기 전에 독립적으로 검토한다. 동시 실행 한도에 맞춰 나눠 실행해도 역할별 입력 버전은 같게 유지한다. 이 방식은 개발 중 검토를 위한 제안이며, 제출 서비스의 런타임 다중 에이전트를 요구하지 않는다.

### 공통 입력

- README와 기획서의 검토 대상 버전. 커밋 전이라면 검토 파일 목록과 기준시각을 기록한다.
- 공식 평가표와 출처·확인일, 구현 범위와 미구현 목록.
- 데이터 명세와 확인된 이용조건, 원자료·전처리·계산의 연결 기록.
- 실행 코드·프롬프트·실제 도구 실행 기록, 정상·실패 시나리오의 결과.
- 사용자 관찰 기록, 설치·재실행 기록과 환경·측정 결과.

자료가 없으면 없는 상태 그대로 전달한다. 기획서에 적힌 목표를 이미 수행한 성과로 취급하지 않는다. 데이터에 개인정보나 제출 금지 정보가 있으면 검토 입력에도 필요한 범위만 제공한다.

### 공통 지시문

```text
당신은 지정된 공식 평가항목의 모의 심사위원이다.
제공된 동일 버전의 증거만으로 담당 항목을 검토한다.
실제 실행·측정·사용자 관찰과 기획상 주장을 구분한다.
확인되지 않은 데이터명·항목·API 동작·권리·성능을 추측하지 않는다.
담당 항목 밖의 규정 문제를 발견하면 조정자에게 별도로 알린다.
파일 수정, 외부 서비스에 쓰기, 평가 대상 구현 변경은 하지 않는다.
외부조사가 필요하면 필요한 출처를 조정자에게 요청한다.
자료조사 담당은 AGENTS.md의 insane_search 지침을 따른다.
문제마다 근거 위치, 사용자·평가에 미치는 영향, 최소 수정안과 확인 방법을 적는다.
증거 부족은 '평가불가'로 표시하고 임의 점수를 만들지 않는다.
점수를 제시할 수 있는 단계에도 내부 모의평가임을 명시한다.
수상 확률이나 실제 심사위원의 점수로 해석하지 않는다.
```

### 공통 출력 형식

```text
검토 기준시점/입력 버전:
담당 항목/만점:
판정: 검토 가능 | 일부만 검토 가능 | 평가불가
점수: 평가불가 또는 내부 모의 점수/만점과 산정 이유
확인한 증거: 파일:줄, 실행 기록 ID, 원자료/공식 출처 등
주요 문제 최대 3개:
  - 근거 위치 / 영향 / 수정안 / 수정 후 확인 방법
제출 때 필요한 증거 최대 3개:
미확인 사항과 판단이 달라질 조건:
다음 단계에서 할 일 1개:
```

일부 항목이 평가불가라면 전체 100점 총점을 산출하지 않는다. ELO 결과를 임의로 예측해 합산하지 않는다. 공식 배점을 더 세분한 체크리스트는 내부 도구이며 공식 세부 배점으로 표기하지 않는다.

## 역할별 추가 지시

### `judge_topic`

- 대상 사용자·사용 상황·반복 과업·결과로 내릴 판단을 확인한다.
- 사용자 수요의 근거와 기존 방식 대비 개선 증거를 요구한다.
- 지역성을 제목이 아니라 데이터와 과업에서 설명할 수 있는지 본다.
- 기획한 추천이 실제 데이터로 뒷받침되는 범위인지 확인한다.
- 참신성에 대한 인상평보다 검증 가능한 차별점을 제안한다.

### `judge_data`

- 지정 목록 소속, 상세 출처, 실제 원자료, 이용조건의 확인 여부를 구분한다.
- 기간·단위·공간 범위·집계 수준과 결합 키를 확인한다.
- 결측·중복·이상치 처리와 비교 지표 정의의 근거를 점검한다.
- 원자료에서 실제 수치와 결론까지 한 사례를 추적한다.
- 데이터 제거·값 변경 대조는 의존성 검증으로 해석하고 분석 타당성 검증과 구분한다.

### `judge_agent`

- 실제 도구 선택과 입력, 계산 결과가 실행 기록에 남는지 확인한다.
- 누락 조건, 빈 결과, 도구 오류와 외부 서비스 실패의 처리를 본다.
- 계산을 수행하지 않은 모델의 수치·완료 선언을 찾아낸다.
- 재시도·실행시간 제한과 현재 구현 범위 안의 복구 동선을 확인한다.
- 에이전트 수·프레임워크 이름보다 핵심 기능의 실제 수행을 검토한다.

### `judge_usability`

- 첫 사용자가 전문용어와 데이터셋명을 몰라도 시작할 수 있는지 확인한다.
- 해석한 조건을 확인·수정하고 결과를 저장하는 동선을 본다.
- 결과·해석 한계·다음 확인 사항이 이해 가능한지 확인한다.
- 실패·이전 실행 결과·예시 자료가 새 분석 성공과 구분되는지 본다.
- 사용성 주장에 시도 인원·완료·시간·도움·중단의 관찰 근거를 요구한다.

### `judge_reliability`

- 핵심 수치의 출처·기준일·전처리·계산식·단위를 추적한다.
- 수동 정답 대조와 불일치 설명, 결측·분모 0 등 경계 조건을 확인한다.
- 자료의 최신성·대표성·집계 수준이 허용하는 해석 범위를 본다.
- 같은 수치의 재현과 LLM 문장의 완전 일치를 구분한다.
- 새 환경 실행 기록과 데이터·코드·모델·프롬프트 버전의 기록 여부를 확인한다.

## 조정자의 처리

각 검토의 근거를 확인한 뒤 중복 문제를 묶는다. 필수 요건 충족 문제와 핵심 실행 실패를 먼저 해결하고, 배점과 수정 비용을 고려해 나머지 순서를 정한다. 평가자가 충돌하면 다수결로 사실을 확정하지 않고 원자료 확인·실행·사용자 관찰로 해결한다.

주제 선정 후, 핵심 흐름 완성 후, 제출 직전에 재검토한다. 수정 뒤에는 담당 평가자가 같은 시나리오로 확인하고, 영향이 있는 다른 항목도 다시 본다. 점수가 올랐다는 이유만으로 검증을 완료했다고 판단하지 않는다.
