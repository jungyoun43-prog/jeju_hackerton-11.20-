# 혼디 — 다음 구현 우선순위

기준일: 2026-11-07 · PRD v0.23 · 최신 실행 증거는 [구현 결과3.23절](implementation-results.md#323-ponytail-제출-패키지-정리)를 따른다.

혼디는 멀리 있는 보호자를 대신해 제주 부모님의 자료·병원 문의·이동·동행 준비를 이어 주는 서비스다. 다음 작업도 **한 번 요청한 준비가 끝까지 이어지고, 막히거나 조건이 바뀌어도 남은 일을 잃지 않는가**를 기준으로 고른다.

이 문서를 후속 작업의 기준으로 관리한다. Research-Wiki에는 이 문서의 링크와 용도만 남기고 할 일 목록을 복제하지 않는다. 아래 구현 상태와 후속 검증을 구분한다. 체크된 항목도 합성 과업에서 확인한 범위를 뜻하며 실제 기관의 업무 성공을 뜻하지 않는다.

### 1. 실제 LLM으로 확인한 고정 합성 사례

고정 입력과 조건은 [평가 정의](../scripts/agent-eval-cases.mjs)를 따른다. 다음은963794d 당시 실행에서 직접 대조한 범위다. 이후 현재 작업 중심 workflow·Prompt·자동 이어가기 변경은 실모델 미검증이며 아래 체크를 새 버전의 통과로 사용하지 않는다.

- [x] 같은 방문의 휠체어 탑승 요청 → 교통약자 이동 문의 경로·자격/승하차 질문, 실제 자격/배차 미확인.
- [x] 합성 보유 자료 불러오기 → 합성 판독문만 준비 상태, 미시행 진찰은 그대로 유지.

### 2. 데이터 보강은 이 순서

1. 기존 병원 후보의 공식 연락처·행정 접수 창구와 돌봄/동행 안내의 현재 확인 범위를 보강한다. 등록 과목을 협진 참여나 환자 수용의 근거로 바꾸지 않는다.
2. 허브859 병원·254 돌봄의 전체 원자료 또는 더 최신의 연결 가능한 공개 자료를 확인한다. 원자료 접근·이용조건·재현 가능성을 먼저 확인하고 표본을 전체 현황으로 확대하지 않는다.
3. 1304 보건지소 관할구역은 공식 파일35행을 연결했다. 229 전문질환센터는5행을 재확인했으나 현재 문의처·수용을 검증하지 못해 미탑재했다. 216 심야약국은 진료 후 약국 방문을 다룰 때 검토한다.
4. 자료별 재취득·정규화·중복/폐업 처리와 기준일·수집일·검증 상태를 재현한다. 갱신 실패 시 기존 확인본과 시점을 유지한다.

센터 이동시간 원자료는 아직 없다. 시간대별 ETA·최적 출발 시각은 이를 확보·검증하거나 적절한 경로 API를 연결한 뒤 검토한다. 카탈로그 수를 늘리기 위한 추가 수집이나 새 DB 도입을 먼저 하지 않는다.

### 7. 실제 AI 전화 한 종류

현재 전화 계획·실패 인계는 구현돼 있지만 발신 사업자와 실제 발신 어댑터는 없다. API 키만 추가해 현재 합성 전화를 실발신으로 바꾸는 작업은 아니다.

첫 범위는 **테스트 참여자가 받는 번호에 일반 접수 절차·준비서류를 문의하는 작업1종**으로 제한한다. 그 뒤 기관과 합의한 업무를 검증한다. 실제 환자정보·기관·위임을 확인하지 않은 상태로 전화하지 않는다.

- [ ] 발신 계정·번호·수신 대상·위임/고지·기록 처리 범위 확정.
- [ ] 별도 작업 ID로 발신 요청과 비동기 결과를 연결. 현재45초 요청 안에서 모든 통화를 기다리지 않음.
- [ ] 결과 웹훅의 출처 검증·중복/역순 도착·타임아웃과 늦은 응답 처리.
- [ ] 무응답 재시도의 실제 예약/실행/철회와 AI 거절·본인확인 시 중단·인계.
- [ ] 구조화된 답변이 다음 문의·서류·이동·동행 조건에 반영. 단순 가능 안내와 예약/배차 확정은 분리.
- [ ] 문의처 변경 시 기관별 이력과 허용 범위를 분리. 이전 기관의 거절을 새 기관에 붙이지 않음.

통화 전사 전체를 LLM 요약만으로 확정 사실로 바꾸지 않는다. 현재는 대상별 한 수신처의 합성 복구 상태이며 여러 기관의 실제 전화 이력 관리·실제 재시도 예약은 후속이다.

### 8. 실제 환자·가족·건강기록 연계

- [ ] 사용자 인증·환자와 보호자의 관계/권한·열람 범위·철회와 데이터 삭제 절차.
- [ ] 환자별 사례 생성/분리와 공유·접근 통제. 현재 고정 합성 환자 화면을 실제 환자 등록으로 표시하지 않음.
- [ ] 승인된 건강정보 고속도로/기관 연계의 신청·시험·운영 조건 확인과 어댑터 구현.
- [ ] 문서의 원문·작성일·출처·수신/확인 상태를 실제 자료에서 검증하고 필요한 업무만 생성.
- [ ] 민감정보 처리·보관·외부 전송, 실제 전화 운영과 서비스 비용 구조에 대한 구체 검토.

지금의 공공 시연 저장소·전역 요청 한도·원점 보호를 환자별 인증이나 개인기록 처리 체계로 간주하지 않는다. 실제 의료진 참여·회신·임상 판단은 별도 실증이 필요하다. 위임 화면의 확인 버튼만으로 이를 충족했다고 표시하지 않는다.

## 우선순위를 뒤로 둘 것

가족 공동 일정·마감 알림은 이어하기와 실제 작업 상태가 갖춰진 뒤 붙인다. 큰 지도·실시간 경로, 범용 공공데이터 챗봇, 여러 모델의 동시 실행, 데이터 개수를 늘리기 위한 수집, 큰 프런트엔드 재작성은 현재 핵심 과업을 막는 근거가 생길 때 검토한다. 기존 지도 링크·JSON/CSV·상태 엔진을 먼저 활용한다.

## 다음 작업을 하나만 고르면

**현재 흐름의 실제 모델 과업 평가와 보호자 참여 관찰**이 다음이다. API 크레딧이 준비된 뒤 명시적 실호출로 정보 부족→질문→후속 준비, 읽기 요청의 비변경, 실패/인계·시각 변경 보존을 확인한다. 과거12과업과 현재 fixture 성공만으로 새 Prompt 품질을 판단하지 않는다. 이어 실제 보호자 참여 과업 관찰로 발견성과 결과 이해를 확인한다. 실제 휴대폰에서 첫 요청→준비 결과 이해→날짜 변경→남은 일을 확인하면서 막힌 지점과 오인을 기록한다. 전화는 발신 계정과 협의된 테스트 번호가 마련되면 한 가지 일반 행정 문의부터 시작한다. 피클은 공개 대행·조건 확인·결과/인계 원칙을 참고했으며 연결 가능한 전화 엔진 API를 확인한 것은 아니다.

완료한 검증은 체크와 상태를 갱신하고 실행 증거를 [구현 결과](implementation-results.md)에 남긴다. 상세 대회 요건은 [제출 추적표](submission-checklist.md), 기능 계약은 [PRD](prd.md), 피클에서 채택한 범위는 [조사 기록](../research/pickle-reference-2026-11-01.md)을 참고한다.
