## 실제로 수행한 흐름

1. explicit http://127.0.0.1:4198/api/agent/capabilities GET에서 llm:false / phone:simulation / healthRecords:demo 확인.
2. 새 PC context와 새 모바일 context에서 폰트와 이미지 decode를 기다렸다. 예시 클릭은 보이는 한 문장만 초안으로 넣었고 보내기 활성화·화면 안 위치를 확인했다.
3. PC에서 기존 고정 preview API 1회 호출 후 실제 렌더링된 답변/기호/닫힌 상세를 확인했다. 모바일은 **그 한 번의 실제 합성 응답을 route replay**해 UI를 확인했다. 모바일에서 새 서버 preview POST를 하지 않았다.
4. 각 화면에서 “다음 문의 초안 넣기”→입력 복귀→초안 수정→“요청 입력으로”를 직접 눌렀다. 수정한 초안이 그대로 남았고 포커스/입력/보내기가 보였다. 보내지는 않았다.
5. 첫 3칸의 native details를 직접 열었다. PC2×2와 모바일 네 칸 한 열이 유지되고 overflow-y:visible이었다. 펼친 상세는 내용 높이만큼 늘고 가로 넘침도 없었다. 초기 목록 건수도 별도 새 GET context에서 열어 확인했다.

“무응답 · 허용 범위 확인”은 여전히 일반 보호자의 말보다 추상적이다. 다만 이제 바로 아래 **“다음 문의 초안 넣기”**가 실행할 동작을 설명하고, 클릭하면 대상과 정리할 내용이 적힌 실제 초안을 읽으며 수정할 수 있다. 이번 범위에서는 진행을 막는 문제로 보지 않는다. 문구 개선만을 위해 기능이나 별도 단계를 추가할 필요는 없다.
