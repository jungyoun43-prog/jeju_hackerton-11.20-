# MVP 구현·검증 결과 기록

기준일: 2026-10-31 · 현재 범위: 대화 UI·허브 계보3종·OpenAI Sol 공개 AWS 연결·DynamoDB 세션/전역 한도. 최신 Ponytail 리팩토링 검증은3.10절, 네 작업창 이전 통합은3.9절, 공공데이터 이전 검증은3.8절, 진료 연결·실패 인계의 이전 검증은3.7절, 실제 모델·저장은 별도 공개 실행 증거를 따른다. 이전 결과는 해당 버전의 범위를 보존한다.

개발 환경은 Linux·Node v22.23.2·npm 10.9.8, 브라우저 QA는 Playwright 1.64.1·Chromium이다. 실행 소스 지문·검사 수·캡처는 검증한 버전의 `orchestration/runs/` 증거를 따른다. 이전 버전의 통과 결과를 새 UI·데이터 버전의 검증으로 대신하지 않는다.

## 1. 문제와 구조

제주 환자와 기존 도외 주치의 사이의 협진 준비에서 보호자가 기관 문의·필요 서류·추가 요청·회신·동행을 연결해야 하는 문제를 다룬다. 환자 진료 장소를 AI가 결정하는 기능은 구현 범위에 포함하지 않는다.

구조는 **텍스트·브라우저 음성 요청 → 공급자 어댑터 → 검증한 도구 → 공개 병원·교통·돌봄 자료와 준비 상태 → 처리 기록·읽기 요약**이다. 공급자가 없는 로컬의 일반 입력은503을 반환하고 원문을 입력창에 보존한다. 기본 고정 preview는 snapshot과 reducer15단계를 실행하며, 별도 진료여정3개·전화실패4개도 같은 도구/reducer로 실행한다. 기관 등록 정보와 합성 문의·회신은 출처가 다르다. 개발 서브에이전트는 별도 worktree에서 작업하며 서비스의 다중 임상 Agent 구조로 설명하지 않는다.

### 3.1 OpenAI 키 입력형 템플릿

사용자 후속 요청에 따라 루트 `.env`의 OPENAI_API_KEY만 채워 실행할 수 있도록 Node env-file→config→Responses API→검증 도구→응답 경로를 구현했다. 기본은 gpt-6.1-sol, 선택은 gpt-6.1-terra이며 두 모델을 동시에 호출하거나 오류 시 다른 모델로 자동 대체하지 않는다. [공식 근거](../research/openai_api_setup_2026-10-31.md)를 기록했다.

- Provider 전용21개와 config·reasoning·실제 Node env-file 부팅5개를 포함한 전체 **148/148** 통과. Node 부팅 검사는 임시 가짜 env와 fetch fixture만 사용한다.
- 대화 화면 **42/42**·기존 수동 흐름 **47/47** 통과. 추가2개는 설정된 모델을 인증 성공으로 표시하지 않는 PC·모바일 capabilities fixture다. 실제 모델·마이크 검증으로 확대하지 않는다.
- 자동규칙 **29/29**, 전용 worktree17개·소유권·출처·키 패턴·실행 지문·롤백 경계 확인. 단위검사와 정적/Lambda 빌드가 통과했다.
- 빈 키 `.env`를 배타적 생성·0600 권한으로 만들고 Git 제외를 확인했다. 기존 파일이 있으면 내용을 읽거나 덮어쓰지 않는다. API 키는 Node 런타임에서만 읽고 브라우저·정적 빌드·제출 ZIP·Git에 포함하지 않는다.
- 도구 호출의 reasoning/encrypted 항목은 요청별 opaque context로 이어주고 HTTP·세션 저장소에 넣지 않는다. 응답1MiB·요청2MiB·출력4,096토큰·40초 호출/45초 전체·8라운드/16도구를 제한한다.
- 읽기 전용 독립 검토에서 설정과 인증의 표시 문제를 발견해 '대화 연결 설정됨·실제 응답은 요청 시 확인'으로 수정했다. 남은 material blocker 없이 ship 판정을 받았다. 검토자는 실제 키·인증파일을 읽거나 유료 호출을 수행하지 않았다.

로컬 `.env`는 AWS에 자동 전송되지 않는다. 현재 공개 데모의 모델은 키 미설정 상태이며 실제 계정 접근·모델 품질·공개 유료 호출의 전역 budget 검증은 별도다.

## 3.3 AWS OpenAI·영속 상태 연결

사용자가 AWS 적용을 요청해 로컬 키를 전용 Secrets Manager에 저장하고, ARN·exact 실행 권한·DynamoDB 상태/예산을 연결했다. 키는 Node→Python OS pipe→AWS CLI stdin으로만 전달했다. 초기 Node child stdin의 Unix socket은 CLI가 /dev/stdin을 다시 열지 못해 실패했고, 실제 OS pipe로 수정한 뒤 가짜 CLI 실프로세스 검사와 실제 업로드를 확인했다. 키·오류 원문·reasoning을 기록하지 않았다.

Agent stack은 UPDATE_COMPLETE이며 직접 코드 게시 `96563ea11b34ac0cdaa743dc3ea8385db69d8f27`에서 다음을 실제 확인했다. 이후 [Actions41205565820](https://github.com/jungyoun43-prog/jeju_hackerton-11.20-/actions/runs/41205565820)도 성공했다. `201f3e68cd9ac8b0fbd40f9ecd5b90c1bea032c7`의 웹/API artifact·OIDC 게시·공개 revision·Lambda code hash가 일치하며 llm:true·Sol을 확인했다. 이 값은 검증 시점 기록이다.

## 3.4 의료 서비스 참고·보호자 설정·진료 준비 화면

후속 사용성 평가의 실제5회 대화에서 첫 복합 요청은16.1초 뒤 LOOP_LIMIT로 중단됐고, UI는 이를 이용 한도 소진으로 표시했다. 좁힌 자료/이동 요청과 날짜 변경은 성공했다. 자세한 기존 결과는 [보호자 역할 평가](reviews/2026-10-31-caregiver-usability.md)에 보존한다.

사용자가 의료 웹사이트를 먼저 둘러보고 REA를 사용하라고 요청해 공식 공개 화면6곳을 실제 비교했다. 굿닥의 탐색, 똑닥의 진료 대상 구분, 닥터나우의 정보 행, Wellthy의 업무/메시지, Birdie 공개 DEMO의 대상자별 작업면, Maven의 가족 이미지와 행동 위계를 참고했다. 관측과 설계 해석·로그인 후 미확인 기능은 [디자인 근거](medical-reference-design.md)에 구분한다. REA는 설치 후 굿닥의 실제 DOM/접근성/스크린샷 Evidence를 확보했고, 별도 One Medical launch 실패는 성공 관찰로 세지 않는다.

왼쪽은 선택적 선호 택시·휠체어·동행 설정, 가운데는 짧은 요청/응답·새 가상 가족 사진, 오른쪽은 행 중심 방문 상태다. 설정3필드만 기기에 보관하고 다음 요청의 실제 도구에 전달한다. 원문 대화·기록·키는 저장하지 않는다. 모바일 서랍·새 대화 소실 확인·음성 인식 후 검토/보내기·안전한 Markdown을 적용했다. 미리보기의 llm:false가 전역 연결 설정을 덮던 문제도 수정했다.

## 3.7 진료 연결 여정·기록 후속 작업·전화 실패 인계

사용자의 후속 요구를 세 전용 worktree에서 구현하고 root에 통합했다. 현재 핵심은 기능의 최초 제공 주장이 아니라 **제주–도외 병원 사이에서 보호자가 반복하는 준비 작업을 줄일 수 있는지 검증하는 것**이다. [공식 비교 조사](../research/care_journey_positioning_2026-10-31.md)는 회사 공개 설명 기준이며 실제 이용 성공과 구분한다.

공통 `getCareJourneySummary`가 세 진료 결과의 근거·원문/작성일/확인 상태·할 일·합성 응답·일정 의존성·공개 데이터 적용 이유를 만든다. 도내 전환/일부 제주/도외 유지는 의료진/기관 근거 없이 선택하지 않는다. 행정 접수 거절을 임상 결론으로 바꾸지 않으며 고정 합성 의료진 근거도 별도로 표시한다. 현재 상태와 다음 행동은 주 화면에, 상세는 진료 연결 여정 창에 있다.

자료 누락→발급 절차→원본/작성일 확보→제출 방식 문의→실제 전달 전 확인을 구분했다. 제출 방법은 원본 확보 전에도 문의할 수 있지만 원본·대리/공유·수신 절차가 준비되지 않으면 실제 전달은 막는다. 병원 휠체어 대여/수령반납, 앉은 채 차량 탑승·승하차/동행인과 지연 시 귀가/동행 재조정 질문이 다음 문의에 반영된다. 시각 변경은 기존 이동·동행 안내를 재확인으로 전환한다.

무응답/AI 거절/본인확인/서류·예약 막힘은 실패 이유·각 시도·담당·연락처/질문·남은 일을 보존한다. 기본 재시도 정책은 미설정이고 해당 대상의 명시적 긍정 요청에서 최초 포함1~3회·1~120분만 설정한다. 같은 정책으로 시도/시간을 초기화하지 않는다. AI 거절·본인확인은 자동 반복을 중단하고 보호자/환자에게 넘긴다. 현재 실제 발신/예약된 재시도는 없다.
