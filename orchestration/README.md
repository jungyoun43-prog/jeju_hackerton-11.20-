# 병렬 개발 하네스

## 규칙

1. UI·Workflow·문서를 각각 별도 Git worktree와 브랜치에서 작업한다.
2. 파일 소유권과 공통 인터페이스는 [초기 계약](../docs/implementation-contract.md), [시각 체계 계약](../docs/editorial-ui-contract.md), [현재 방문 지원 계약](../docs/visit-support-contract.md), 기계 판정 대상은 [rules.json](rules.json)을 따른다.
3. 각 담당자는 다른 작업자의 파일을 수정하지 않는다. 의존성 변경·인터페이스 변경은 통합 담당자에게 먼저 알린다.
4. 외부 조사에는 insane-search를 사용하고 URL·확인일을 남긴다. 시연과 실제 운영 상태를 구분한다.
5. 완료 시 변경 파일·검사 명령·결과·미완료 항목을 전달하고 자기 브랜치에 커밋한다. 통합 담당자는 커밋 단위로 반영한다.
6. 필수 검사 실패는 해당 작업에 되돌려 수정하며, 이미 통합한 변경은 `git revert <해당 커밋>`으로 되돌린다. `reset --hard`나 다른 작업자의 변경 삭제는 하지 않는다.
7. 완료·대기 상태의 에이전트에게 보완을 맡길 때는 새 작업을 시작하는 follow-up을 사용한다. 메시지 전달만으로 재실행됐다고 판단하지 않으며 실제 실행 상태를 확인한다.

## 관측·평가

`npm run observe`는 작업 브랜치·변경 파일·검사 상태를 표시하고, `npm run eval`은 파일 소유권·시연 상태·도메인 수락 기준·빌드 등 자동화 가능한 항목을 평가한다. 아직 구현 전인 항목은 통과 처리하지 않는다. 실행 결과는 `orchestration/runs/`에 기록한다.

자동화된 규칙의 준수율과 전체 제품 품질은 서로 다르다. 의료적 타당성·실제 개인정보 적법성·데이터 재배포 권한·기관 연동은 별도의 미검증 항목으로 남긴다. 오류를 발견하면 원인·수정 규칙·재검증 결과를 회고에 기록한다.

## 기준선과 배포

최초 기준선은 `e1e7e44`이며, 후속 작업은 각 계약의 기준 커밋을 사용한다. 사용자가 AWS 배포·CI/CD를 요청했으므로 통합 담당자가 검증된 커밋을 GitHub main에 게시하고 실제 Actions 결과와 공개 배포 SHA를 확인한다. 작업 에이전트가 각자 원격 게시나 AWS 변경을 수행하지 않는다.
